# Desktop Splat Wallpaper Engine Design

## Product Shape

This is a macOS live wallpaper app for Gaussian splats. The wallpaper looks still during normal work, but can be made interactive when the user wants to play with it. In interaction mode, dragging changes perspective, scrolling zooms, and the current camera can be saved as the resting wallpaper view.

## Core Decisions

- Target macOS first.
- Build as a menu-bar utility, not a full document editor.
- Use local files first. No cloud dependency in the MVP.
- Treat `.ply` as the source format and `.sog` as the preferred runtime format.
- Use a native desktop-level window instead of Apple's static wallpaper API.
- Avoid depending on official Wallpaper Engine because it does not support macOS.

## Why Not Apple's Wallpaper API

AppKit can set a desktop image through `NSWorkspace`, but that API points at image files. It does not provide a public interactive 3D wallpaper renderer. The practical approach is to create a borderless window placed at the desktop layer and render into that window.

## Architecture

```text
Menu bar app
  -> wallpaper window controller
  -> renderer host
  -> splat scene loader
  -> camera state store
  -> power/performance policy
```

## Components

### Menu Bar App

Owns app lifecycle, scene selection, interaction toggle, pause/resume, and settings.

### Wallpaper Window Controller

Creates one borderless window per selected display. The MVP can support only the main display. The window should sit behind normal app windows and avoid stealing focus during passive mode.

### Renderer Host

Renders the splat. The first prototype can use a web renderer if that makes `.sog` loading faster to prove. A later native renderer can replace it if performance or input behavior requires Metal.

### Splat Scene Loader

Accepts `.sog` for MVP. It should reject ordinary point-cloud or mesh `.ply` files unless a conversion step has created a runtime splat format. The first prototype copies the selected `.sog` beside the bundled viewer files so the embedded WebKit renderer can load viewer code and scene data from one narrow file-read scope.

### Camera State Store

Persists orbit target, position, rotation, field of view, and zoom/resting state.

### Power Policy

Runs at low or zero animation cost when idle. Raises frame rate only during interaction or camera transitions.

## MVP Milestones

1. Create native menu-bar app shell. Done.
2. Open a desktop-level wallpaper window on the main display. Done.
3. Render a known local `.sog` in that window. In progress with bundled SuperSplat viewer.
4. Toggle interaction mode without disrupting normal desktop use. Done at window-event level.
5. Save and restore camera state.
6. Add low-power idle behavior.

## Risks

- Desktop-level window behavior can be finicky across Spaces, Mission Control, multiple displays, and full-screen apps.
- Web renderer embedding may be faster to prototype but harder to make feel fully native.
- Native Metal rendering may perform better but costs more implementation time.
- Not every `.ply` is a Gaussian Splat PLY. Some PLY files are meshes or sparse point clouds and cannot be used directly.

## Initial Verification

- App launches as a menu-bar utility.
- Wallpaper window appears behind regular windows.
- A `.sog` scene renders visibly.
- Dragging changes perspective only in interaction mode.
- Idle mode lowers CPU/GPU activity.
